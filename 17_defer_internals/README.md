# deferの内部動作

deferはGo特有の制御構造で、関数の終了時に後処理を確実に実行するために使われます。
内部的にはdeferされた関数呼び出しはスタックに積まれ、LIFO(後入れ先出し)の順序で実行されます。

# deferの実行順序(LIFO)

DeferOrder関数では3つのdeferを順に登録しています。
実行順序はLIFOであるため、最後に登録されたdeferが最初に実行されます。
結果として、third、second、firstの順にスライスに追加されます。

# クロージャによる変数キャプチャの落とし穴

DeferWithClosureBug関数では、ループ変数iをクロージャ内で直接参照しています。
すべてのクロージャが同一の変数iを共有するため、実行時にはループ終了後の値が使われます。

DeferWithClosureFix関数では、i := iによってイテレーションごとに新しい変数を作成しています。
各クロージャが独自のコピーを持つため、期待通りの値が得られます。

# ループ内でのdeferの問題

DeferInLoop関数では、ループの各イテレーションでdeferを登録しています。
deferは関数の終了時にまとめて実行されるため、ループ中はすべてのdefer呼び出しがスタックに蓄積されます。
ホットループでdeferを使うとメモリ使用量が増大し、パフォーマンスが低下する原因になります。

# 名前付き戻り値のdefer内での変更

DeferModifyReturn関数では、return文で戻り値を1に設定した後にdeferが実行されます。
deferされた関数は名前付き戻り値resultに直接アクセスできるため、result += 10によって最終的な戻り値が11になります。
この挙動はエラーハンドリングのパターンでよく活用されます。
